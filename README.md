# PlayAuto

项目目录与 Gradle 项目名称为 `playAuto`，
GitHub 仓库为 https://github.com/CuiYao631/playauto。
目录改名不改变 Android 包名或已安装应用的数据。

PlayAuto 是用于重建 AutoPlay 车载盒子连接流程的 Android 应用。
应用显示名称为 PlayAuto，首页标题为 CarPlay，不显示副标题。
为保持兼容，包名、偏好设置存储名称、既有 APK 输出名称及诊断日志标签保持不变。

应用启动或收到 USB 插入事件后，会查找支持的盒子、申请 Android USB 权限、
占用包含批量输入/输出端点的接口，并启动协议握手。
收到有效的 `CMD_OPEN` 后，每 2 秒发送一次原版 `CMD 170` 心跳以维持会话。
手机自动连接由界面设置控制，同时受盒子能力、已配对设备及当前连接状态约束。

## 界面与图标

- 启动器图标直接使用用户提供的 PNG，不添加自适应图层、背景、留白，
  不对原图进行缩放处理或重绘；应用内首页 Logo 保持不变。
- 图标源文件位于 `app/src/main/assets/icon/`。
  清单引用 `@mipmap/playauto_launcher`：
  `favicon-48x48.png` 原样复制到 `res/mipmap-mdpi/playauto_launcher.png`，
  `favicon-192x192.png` 原样复制到 `res/mipmap-xxxhdpi/playauto_launcher.png`。
  Android 自行选择和缩放最接近的密度资源，不生成额外缩放图片。
  16px/32px 图标不用于启动器，512px 图片仅保留为源素材。
  更新素材时也应原样替换；启动器仍可能自行添加遮罩或调整大小。
- 首页 Logo 与标题整体居中，右上角保留设置按钮。
  从投屏返回时保持相同布局，不重复为窗口已经预留的系统栏空间添加内边距。
- 页面淡入时的窗口背景与当前主题同步，包括运行期间切换明暗主题的情况。
- 首次使用和恢复默认设置后采用深色主题；已明确选择的浅色或跟随系统设置会保留。
  启动窗口默认为深色，运行期间页面遵循所选主题。
- 应用对话框统一使用明暗主题、12dp 卡片圆角、配套背景色及绿色 48dp 操作按钮。
  选项、输入、确认及校验行为不变，不修改 Android 系统权限对话框。

## Android 兼容性

Gradle 与手动 APK/D8 构建的最低版本均为 **Android 4.4（API 19）**，
目标版本为 Android 15（API 35）。

- API 19–20 使用基于 Holo 的明暗主题、按压状态按钮背景和 PNG 启动器图标；
  API 21 及以上保留 Material 样式和水波纹效果。所有版本均使用原始 PNG，
  不使用自适应图标图层。
- 仅 API 23 及以上动态申请麦克风权限，旧系统使用安装时权限。
  PCM 录音/播放兼容旧版阻塞式字节数组接口；API 21 之前使用双声道音量控制。
- API 21 之前使用旧版 H.264 解码器枚举和输入缓冲接口。
  这些系统只能报告解码器是否存在，不能查询支持的分辨率范围；
  实际配置失败会显示错误，不会将未经验证的分辨率标记为可用。
- API 19–20 使用 `RemoteControlClient` 处理后台媒体按键，
  API 21 及以上使用 `MediaSession`。
  通知渠道、前台服务类型、可变/不可变 PendingIntent 和广播注册标志均按版本处理。
- API 23 之前，悬浮窗入口检查安装时权限并打开应用详情，
  不调用不存在的悬浮窗授权页面。厂家权限和 AppOps 策略仍可能限制该权限。
- APK 包含原版 `libnx1.so`，支持 `armeabi`、`arm64-v8a` 和 `x86`。
  ARM32 导入符号已与 API 19 NDK 系统库核对。
  原生库加载与依赖真实盒子的加密/握手验证分开进行。

历史验证记录：Android Lint 未发现 API 兼容性错误；
API 28 模拟器曾通过当时的 117 项断言。
API 22（Android 5.1）ARM64 模拟器曾通过 12 项兼容性断言，
覆盖明暗设置页面、启动器渲染、原生库加载、PCM 输入/输出和旧版媒体控制注册。
这些记录**不代表已在 Android 4.4 上完成运行验证**：
当前 Apple Silicon 环境没有可运行的 API 19 镜像。
启动、ARM32 库加载、USB 通信、解码和手机投屏仍需真实 API 19 车机验证。

需要手动执行兼容性测试时，可先运行 `./build-apk.sh`，
在已连接且已授予麦克风权限的设备上执行：

```sh
COMPATIBILITY_TEST=1 ANDROID_SERIAL=<device-serial> sh ./test-connection-service.sh
```

## USB 连接与权限

从原版 USB 过滤配置恢复的设备标识：

- VID `0x1314`，PID `0x1520`
- VID `0x1314`，PID `0x1521`

连接详情仅显示盒子和手机的简短状态：
**未连接 / 连接中 / 已连接 / 连接失败**，并提供关闭按钮。
不显示协议、解码及 USB 诊断信息，也不提供 USB 授权或连接重试按钮。
等待授权时拔出设备会清除待处理标记，重新插入后可以再次申请；
是否显示授权界面仍由厂家系统控制。

Android 4.4（API 19–20）清单还声明了原版使用的特权
`android.permission.MANAGE_USB`。
只有该权限实际获准、检测到目标盒子且 Activity 可见时，
才会在普通授权弹窗之前尝试 `libnx1.so` 中的原版 `BoxCore.stUsb` 辅助接口。
是否打开盒子以重新检查的 `UsbManager.hasPermission` 为准，
不以辅助接口返回值为准。
缺少权限、库加载/链接失败及授权无效等信息保留在高级 USB 诊断中，
普通权限申请仍然可用。API 21 及以上不使用该旧版辅助接口。

安装为系统应用不代表已经获得 `MANAGE_USB`。
高级设置分别显示系统应用身份、实际管理权限及旧版授权尝试结果。
已有系统安装应通过车机正常的系统应用管理流程更新 APK，并重启后检查；
特权权限的分配由固件决定。
不要为了该路径向 `/system/lib` 复制无关库或修改权限：
`libnx1.so` 已包含在 APK 中，库文件模式 `664` 也不等于 USB 授权。
旧版授权路径仍需 Android 4.4 实机验证，模拟器不能证明其可用。

### USB 通道

应用固定使用 **Android USB**，不再提供通道切换项。
服务启动时会清除以前保存的 Native USB 选择。
Native USB 实现和库文件仍保留，但应用不再选择该路径。

保留的 Native USB 实现使用未修改的原版 `libconnection.so`
（`armeabi`、`arm64-v8a`、`x86`），沿用原版 JNI 类名和方法名。
它仅打开 Android 已发现的受支持 VID/PID，并复用相同的协议、加密、
音频和视频链路。USB 传输与 OpenH264 解码相互独立；
原版原生音频处理库仍未集成。

该实现基于 libusb，要求固件允许访问 USB 设备节点和枚举资源。
Android USB 弹窗授权或系统应用身份都不能保证节点可访问，
SELinux 仍可能拒绝。库加载、初始化、打开和传输错误均明确报告。
该路径不会执行 Root 命令、修改权限或安装系统库。
`stUsb` 与普通 Android 授权弹窗属于 Android USB 路径，
不能将 Android 授权视为 Native USB 节点权限的证明。

保留的适配器将单次传输限制为 16 KiB，原生调用最长等待 1 秒。
支持同时输入/输出，但释放库的进程级全局上下文前会等待在途调用结束。
原版 JNI 在错误（包括 libusb 超时）时不返回部分传输长度，
因此负数传输结果会结束会话，避免协议字节丢失或重复。
这种保守处理可能在空闲超时时断开。
模拟驱动测试覆盖缓冲偏移、长度限制、错误及所有权；
模拟器成功加载库不等于 Android 4.4 ARM32 实机通信可用。

## 高级功能与 Root

### 隐藏的高级页面

高级功能默认隐藏。连续点击 **设置 → 软件版本** 四次，
相邻两次间隔不超过 3 秒，即可解锁并进入页面。
此后 **更多设置 → 高级功能** 仅在当前进程内可见。
解锁状态不保存到偏好设置，进程重启后重新隐藏；
屏幕旋转、主题切换和前后台切换不会重新锁定。

页面保留 Root 状态、独立 Root 身份申请、系统应用身份及实时 USB 诊断。
Root USB 授权和转为系统应用的界面操作已经移除。
打开高级页面不会执行 `su`。

Root 状态仅表示当前进程最近一次明确检查的结果，不代表永久授权。
只有成功确认 UID 0 才显示 **已授权**，否则显示 **未授权**；
详细输出保留在申请结果对话框中。进程重启后恢复为 **未授权**。
Root 管理器中的授权发生变化后，需要重新申请确认。
USB 诊断在服务状态变化和返回应用时刷新。
返回键进入更多设置，主题/旋转重建后仍保留高级页面。

### 申请 Root 权限

**高级功能 → 申请 Root 权限** 经确认后立即执行真实的 `su -c id`，
不要求连接 USB 设备或连接服务。
仅当命令退出码为 0 且 `id` 输出确认 UID 0 时认定授权成功。
拒绝、缺少 `su`、超时及非 Root UID 均明确显示。

该操作不会给设备获取 Root、修改 USB 授权或让应用进程长期以 Root 运行。
是否弹出授权提示或复用已有批准由 Root 管理器决定。
执行在后台完成，并有等待时限及重复请求保护。

### 已移除的实验性 Root USB 授权

以下仅记录保留的内部辅助代码，不是当前可用的界面功能。
历史操作需要用户明确确认，不会自动申请 Root，也不是获取 Root 的工具。
要求设备已经 Root、`su` 管理器可用、使用 Android USB，
且只连接一个受支持盒子。没有盒子或 Android 已授权时不执行 `su`。

辅助代码通过 `su -c` 和 `app_process` 运行随包提供的 `RootUsbGrant`，
校验 UID 0、请求 UID 与已安装 PlayAuto 包的一致性，
重新枚举指定的受支持 VID/PID，再通过反射调用系统 USB 服务的
`grantDevicePermission(UsbDevice, uid)`。

它不使用硬编码 Binder 事务编号，不安装文件、不修改设备节点模式、
SELinux 或应用的 `MANAGE_USB` 权限。
厂家接口差异、隐藏 API 限制和 Root 管理器拒绝都可能导致失败，
不能保证绕过厂家禁用的 USB 授权界面。

执行不阻塞主线程，拒绝重复请求，等待 `su` 最多 30 秒，输出长度受限。
授权前还会检查原始单调时钟截止时间，过期批准不会触发延迟授权。
内部诊断保留退出/错误输出和之后实际检查的 `UsbManager.hasPermission` 结果。
退出码或成功标记本身都不能证明授权，只有确认授权后才可启动 Android USB。
Native USB 节点访问权限与此无关。

USB 授权通常在拔出或重启后失效。
开机、插入设备及重试时均不会自动请求 Root；
历史操作每次都需要手动触发，Root 管理器可以按其策略保留批准。

### 已移除的 Android 4.4 系统应用转换

**转为系统应用** 的界面及 Activity 操作流程已经移除。
以下用于说明历史辅助实现及已有安装记录，不是当前应用可执行的操作。

历史实现仅支持 API 19–20：先单独确认 Root 只读检查，
再单独确认写入 `/system/app/PlayAutoReplacement.apk`。
辅助代码检查已安装包的 UID 和来源，要求独立的 ext4 `/system`，
拒绝 SELinux enforcing、已有目标/暂存文件/记录/备份及空间不足等情况。
它不是适用于现代 Android 或 Magisk 的通用系统化工具。
打开页面本身不会修改文件。

KitKat 系统应用从 `/system/lib` 解析 JNI。
转换时还会复制当前安装 ABI 的 `libnx1.so`、`libconnection.so`
和 `libopenH264decoder.so`，保留用户安装中的原始库。
已有系统库仅在 SHA-256 一致时复用；内容不同会明确报冲突，
在预检查阶段停止，不覆盖任何已有系统库。

只读检查显示复制/复用计划，安装前再次检查，空间预算包含缺失的库。
每个新增库先复制到固定的隐藏暂存路径，执行 fsync、校验哈希，
设置 root:root / 0644，再发布。全部库验证完成后才发布 APK。
拒绝符号链接库路径和预先存在的暂存文件。

原用户安装保留，另在应用的 `files/system-app-original.apk` 保存备份。
APK 同样通过固定暂存路径、fsync 和 SHA-256 校验，
设置 root:root / 0644，并在发布库/APK 前将摘要、库哈希、
创建/复用归属写入 `/system/.playauto-replacement-install`。
只读系统挂载会在操作时重新挂载，并在 `finally` 中恢复；
恢复失败会明确报告。

异常残留文件不会静默删除或覆盖，断电/中断后可能需要人工恢复。
执行前应有独立的车机恢复方案和系统备份。
Root 批准需在 30 秒内到达，整个流程另有 2 分钟等待预算，
以完成复制和挂载恢复。超时仅表示结果未确认，
不表示没有写入；重试前必须检查。

流程不会自动重启、卸载、修改全局权限或 SELinux。
需要手动重启并确认系统应用身份和 `MANAGE_USB`，
复制成功不能证明这两项已经生效。

历史撤销操作需明确确认，只删除同时匹配记录摘要和保留备份的固定系统 APK，
并要求匹配的原始应用已经安装在 `/data/app`。
若正从 `/system` 运行，应先将备份安装为用户更新。
撤销保留备份和用户安装，需要手动重启；已变化的文件拒绝删除。
库文件也要验证记录哈希，仅移除本次新建的库，不删除复用库；
删除前要求用户安装中存在独立且一致的原生库副本。
其他应用可能依赖这些共享库名，存在依赖时不能撤销。
旧版仅记录 APK 的安装记录不授权删除任何系统库。
恢复备份前不要卸载应用或清除数据。

写系统、重新挂载及重启流程尚未在真实车机上验证。
本地测试不能写入 `/system`，仅验证防护条件和复制完整性。

## 视频解码、背压与花屏恢复

H.264 压缩帧存在依赖顺序。解码器输入缓冲暂不可用时，
解码线程保留最早尚未提交的帧，不丢弃，也不移到新帧之后。
重试前先取出解码输出，并处理输出格式变化；
输入连续阻塞 1 秒会明确报告解码错误。

队列限制按原版约 2 秒阈值（`fps * 2`）设置，
不再因仅积压 3 个包就重置整条参考帧链。
Surface 有效时，即使没有新输入，线程也会持续取出延迟输出，
不依赖下一个 USB 包触发。

队列溢出会清除依赖链并使待提交输入失效；
只有具备 SPS/PPS 和 IDR 时才重新创建解码器，
同时以限频方式请求关键帧。
解码异常也会清理压缩数据并请求恢复，不继续使用损坏的参考帧链。
`AutoPlayVideo` 记录溢出、所选解码器/尺寸/模式、输出格式及错误。

这些修复针对已知的软件丢帧路径，
**不能证明 Android 4.4 硬解花屏已经全部解决**。
仍需真实盒子/手机验证，并与软件解码结果比较。

### 原版 OpenH264 软解链路

**设置 → 解码方式 → 软解（原版 OpenH264）**
使用未修改的原版 `libopenH264decoder.so`
（`armeabi`、`arm64-v8a`、`x86`），沿用原版 JNI 类名和方法名。
界面只提供原版软解和默认硬解两个选项：
旧自动选择迁移为硬解，旧系统软解选择迁移为原版 OpenH264。
OpenH264 固定通过 GLES2 渲染，不受硬解的 Surface/Texture 选项影响。

已对照原版 `O0_0Ooo/OO___.java` 及对应 smali：
软解分支将 Annex-B 数据交给 `OpenH264Decoder.decodeFrameOffset`，
将紧密排列的 I420 输出拆为 Y、U、V 三个平面，
通过 GLES2 亮度纹理显示。
当前实现沿用相同的库、平面布局、纹理方向及有限范围 BT.601 转换。
尺寸来自原生解码器，不猜测原生 stride。

进程级独占所有权保护原版 JNI 的全局状态，
错误明确上报，不静默切换其他解码器。
继续保留有界队列、IDR 恢复及当前应用的等比适应/触摸坐标计算，
没有整体复制原版界面。
原版硬解是独立的 MediaCodec 链路；
仅包含 OpenH264 库不会使硬解模式变成原生软解。

现有默认仪器测试包含真实原版库解码、原生所有权/释放、
Y/U/V 数值及队列溢出后的 GLES2 Surface 像素检查。
这不代表 Android 4.4 ARM32 性能或手机/USB 连续性已验证。

可选的**系统 MediaCodec** 像素回归使用本地生成的灰色
Baseline SPS/PPS/IDR 数据，主动造成队列溢出后通过 PixelCopy 检查。
需要手动验证时，先构建并安装测试 APK，再执行：

```sh
adb shell am instrument -w -e videoPixels true cn.autoplay.replacement.tests/cn.autoplay.replacement.ConnectionServiceInstrumentation
```

该项在当前模拟器上尚未通过，出现过黑色解码输出或没有 Surface 输出，
因此不包含在默认生命周期回归中，结果明确报告 `video_pixels=not_run`。
生命周期回归通过不能视为系统 MediaCodec 像素验证或实机验证通过。
原版软解像素验证有独立的 `openh264_pixels` 结果。

### 与原版主屏对齐的显示选项

保留当前界面，对照原版 `SettingsViewModel`（`_Oo/_o_.java`）、
`MyApplication`、`VideoSize`（`_O_O_/O_O0_0_0O_.java`）、
`AvcDecoder` 和视图管理器核对设置值及运行链路。

- 普通硬解默认 30fps，使用 `MediaCodec.createDecoderByType` 和 SurfaceView。
  保留原版 Freescale/Huawei 特定设备默认 60fps 的规则。
  与原版一样使用系统 AVC 选择器，不强制按解码器名称过滤，
  不静默切换原生软解。
- 帧率提供 60、55、50、45、40、35、30、25、20 九档。
  保存实际 fps，而不是旧版两档索引；已有明确的 30/60fps 选择会迁移。
  OpenH264 按原版 `send_g_open` 软解分支固定请求 25fps、DPI 160，
  硬解设置保留，切回硬解后可继续使用。
- 分辨率使用原版以 5% 为步长缩放、偶数像素取整、缩小列表简化为三档，
  并保留 1088×768 / 1920×1152 特殊尺寸。
  默认使用当前显示端的物理尺寸，支持竖屏。
  选项保存具体尺寸，不保存依赖屏幕的索引；旧 720p/1080p 仍可用。
  不提供超过既有协议 4000 像素限制的尺寸。
- 投屏 DPI 提供自动/120/160/240。
  自动值使用原版等比 720 行参考画布及整数/浮点计算公式。
  已保存的 320 值作为旧版选项保留。
- 默认图像比例遵循原版同方向填满、横竖方向不同时保持比例的行为。
  已明确选择的等比适应设置保留。
  继续使用修正后的比例计算，不复制反编译代码中的整数除法缺陷。
- 运行时修改分辨率、帧率或解码方式会更新服务，
  使用当前盒子版本码重发 `CMD_OPEN`。
  固件可能仍要求手机/盒子重连，写入成功不代表设置已应用。
- 硬解初始化沿用原版 frame-rate/operating-rate，
  SPS/PPS 随码流提交并在输入背压时保留。
  软解保持原版 JNI I420 + GLES2，Surface/Texture 仅用于硬解。

对齐范围是原版的**主投屏链路**，不是完整移植所有厂家专用视口、
仪表屏/副屏配置或原版可选的硬解 OpenGL 后处理。
这些独立分支不宣称已支持。
选项对齐或模拟器测试通过均不能保证真实车机花屏已解决。

- 投屏夜间模式默认跟随手机，也可手动开/关。
  旧时间编辑器和定时任务已移除，旧定时值忽略。

- 解码选择：原版硬解 MediaCodec 或 OpenH264 + GLES2 软解。
  请求的解码器不可用时明确报错，不静默回退。
  硬解可在 SurfaceView 和 TextureView 之间切换。
- 字体大小、系统导航栏显隐、导航/替代音频压低媒体音量、
  音频调试（本地测试音及手机媒体控制）。

盒子设置在握手成功前排队，新会话建立后重新发送。

保存或写入不代表固件支持，未擅自推断新的盒端确认机制。
导航压低音量使用音频流类型 2，也包含其他替代提示音；
流停止后恢复媒体增益。本地恢复默认不会重置盒子保存的名称和配置。

按要求已移除 iPhone/Android 应用模式、应用语言及悬浮窗占位项。

HiCar 等投屏协议，并非安装手机应用。
当前保留 CarPlay，不显示尚未支持的协议选项。
真实盒子的视频、音频、按键和固件设置都需要硬件验证，模拟器不能代替。

### 方控学习与厂家广播

方控学习有独立页面和六个功能块，横屏三列、竖屏两列：
上一曲/接听、下一曲/挂断、播放/暂停、Siri、投屏主页、投屏返回。
页面显示绑定结果，支持取消学习和确认清空。
选择功能后按下并松开按键即可绑定；
重新学习同一按键会替换它原先的功能。
离开页面、切换应用或重建布局会取消按键捕获。

组合功能使用盒子音频控制 14/4/5 判断来电、通话中和通话结束。
原版命令 300 接听、301 挂断、205/204 切歌、5+6 激活 Siri、
200 返回投屏主页、106 返回。
学习绑定优先于可选的音量键切歌映射。
通话动作依赖固件通话状态上报；
真实手机/盒子兼容性仍需验证，尤其是 Android Auto 导航相关行为。

按键、学习功能、绑定及已排队的线缆命令记录到 `AutoPlayKeys`：

```sh
adb logcat -s AutoPlayKeys:I '*:S'
```

学习页在清除绑定按钮下方显示最近 50 条按键日志，最新在前，
未处于学习状态时也记录。
清空日志只清理日志，不清理绑定，后续事件继续显示。
日志包含按下/松开、按键名/键码、扫描码、重复次数及映射动作。
原始 Activity 按键仅在学习页或映射控制时记录，
不记录其他位置的任意文字输入。
被 Android 提前拦截的系统按键无法在应用中记录。

页面提供 **默认** 和 **长安 CS35Plus** 两种协议。
默认仅接收 Android 按键，CS35Plus 额外接收已确认的厂家广播。
两种协议的 Android 绑定独立，Activity 和媒体会话查询均使用各自绑定。
已有 Android 绑定保留在默认协议；
旧厂家绑定一次性迁移到 CS35Plus，不覆盖已有目标绑定。
初始协议仍为默认。

切换协议会取消学习、重置按住/防抖状态并清空页面日志；
清除绑定只影响当前协议。
CS35Plus 在前台动态接收 `com.coagent.intent.action.KEY_CHANGED`，
读取字符串参数 `Key_code` 和 `Key_state`。
NEXT/PRE/VR 要匹配 DOWN/UP 才完成学习；
MAIN 是触摸按钮，只需 DOWN，不要求 UP。
四个厂家按键默认均未绑定，保存为 `steering_cs35plus_vendor_<key>`。
CS35Plus 的 Android 绑定保存为 `steering_cs35plus_key_<keyCode>`，
默认协议仍使用 `steering_key_<keyCode>`。

绑定广播仅在 Activity 已恢复且手机已连接时于 DOWN 执行一次，
抑制重复事件，MAIN 使用 350ms 防抖。
未知按键/状态不执行，学习期间只捕获，不控制。
不同 Android/媒体会话/厂家来源的相同动作在 350ms 内去重，
这只是启发式规则，不是共享硬件事件 ID。
日志仍限制为 50 条，页面暂停时注销接收器。

厂家日志记录真实的 `isOrderedBroadcast()` 和 `FLAG_RECEIVER_NO_ABORT`，
包括无效或不支持的事件。
该信息仅用于诊断，不提高优先级，也不终止广播。
普通广播无法通过 abort 阻止；
带 NO_ABORT 的有序广播也不能依赖该机制拦截。
有序且无 NO_ABORT 仅说明可能值得后续测试，
不代表应用首先收到，也不能撤销系统已经执行的动作。
合成测试不能确定真实车机的广播投递方式。

接收器必须导出才能接收车机广播，但目前没有已确认的发送方权限，
其他应用可能伪造广播。
手动绑定及前台/连接门控只能限制作用范围，不能认证发送方。
不要将其用于安全关键操作，也不能阻止车机自身的 MAIN/主页行为。
已确认车机 NEXT/PRE/VR 的 DOWN/UP 及 MAIN 的 DOWN 投递；
实际 CarPlay 控制及重复时序仍需真实手机/盒子验证。

## 显示端旋转与视频缩放

首页右上角仅保留设置按钮。
蓝牙和 Wi-Fi 图标位于设置页 **环境检测** 左侧，
各自连接时点亮，点击无背景的 Wi-Fi 图标打开连接详情。
不再设置独立的连接状态区域，页面打开期间图标随状态更新。
连接详情只显示盒子和手机的简短连接状态。

首页仅显示 USB 未插入、查找中、连接中、未配对或连接失败等简短提示。
连接期间 Logo/标题保持静止可见，提示文字后显示 18dp 绿色加载圆环，

高度较小的横屏页面使用紧凑的纵向 Logo/状态布局，
避免提示文字与 Logo 重叠，并遵循左右系统安全边距。

默认请求的 CarPlay 画布跟随**运行 PlayAuto 的显示端**当前屏幕尺寸。
显示端旋转时，服务在不断开 USB 的情况下更新请求宽高；
手动分辨率也会交换宽高以匹配当前方向。
渲染器重新适配并请求关键帧，
盒子和手机是否接受新的画布请求仍需实际确认。
这里的显示端旋转与连接盒子的 CarPlay 源手机旋转不是同一件事。

同方向默认使用原版 **拉伸全屏**，横竖方向不同时自动保持比例。
仍可选择 **等比适应**，已有明确的 `video_scale_mode` 选择会保留。
旧 `aspect_mode` 已由 `video_scale_mode` 替代，触摸坐标始终相对视频视图计算。

历史验证：API 28 模拟器在 1080×2350 / 480 dpi 下，
当时的仪器套件通过了 45 项关于首页边界、活动视图旋转/比例和服务生命周期的断言。
合成视频尺寸仅验证视图几何，不验证真实盒子解码或手机投屏，
也不代表后续旋转修改已经经过实机验证。

## 后台连接

点击 **后台连接** 文字旁的浅灰色圆圈感叹号查看说明，
不再显示单独的说明行，开关行为不变。

**更多设置 → 后台连接** 默认开启，恢复默认后也开启。
绑定的 `ConnectionService` 负责 USB 权限/拔出、协议会话、心跳、
PCM 播放、麦克风上行、媒体控制及投屏夜间模式。
应用可见且连接到已授权盒子后，服务升级为已启动的前台服务，
显示常驻连接通知。
仅在已连接且后台连接开启时持有部分 CPU 唤醒锁；
未连接盒子时不需要前台服务或唤醒锁。

切换应用或销毁/重建 Activity 不会关闭服务持有的活动连接。
Activity 隐藏时暂停视频投递，返回后附加到已有会话并请求关键帧，
不重新进行 USB 握手。通知打开现有主 Activity。
关闭后台连接会移除前台保护和唤醒锁；
Activity 存在时绑定服务仍可工作，最后一个 Activity 解除绑定后，
服务销毁并关闭 USB 和音频。

麦克风仍需明确授予 `RECORD_AUDIO`。
Android 11 及以上仅从已获授权的可见 Activity 准备后台麦克风访问。
切换应用前未授权时，需要返回 PlayAuto 授权。
只有手机请求时才录音，不会仅因服务运行就录音。
Android 13 拒绝通知权限不会阻止前台服务执行，
但可能使通知不在通知栏显示。

该机制不能抵抗强行停止、进程终止、USB 拔出或车辆断电，
不保证进程死亡后自动恢复。
必要时在厂家设置中允许后台运行并解除电池限制。
端到端连续性仍需真实盒子/手机测试。

## 开机自动启动

在设置中打开 **开启自动启动**，默认关闭。
点击文字旁的浅灰色圆圈感叹号查看说明，不再显示单独说明行。
清单广播接收器在设备解锁后处理 `BOOT_COMPLETED`，
读取与界面开关相同的持久化设置。
关闭开关或恢复默认会禁用开机启动并清除待处理启动通知。
该设置不改变原有 USB 插入行为。

Android 9 及以下由接收器直接请求打开主 Activity。
Android 10 及以上若尚未获得系统悬浮窗权限，
则发送可点击的启动通知，不尝试被禁止的后台 Activity 启动。
Android 13 及以上在开启功能时申请通知权限。
通知回退**不是无人值守自动启动**；
车机自启动白名单和电池限制仍可能需要手动配置。
拒绝或屏蔽通知会使回退通知不可用，接收器记录原因。
接收器不会启动后台服务或麦克风。

首次安装后必须手动打开一次。
强行停止的应用在再次手动打开前不能接收开机广播。
解锁前 Direct Boot、USB 触发启动定制、
手机连接后自动将应用切到前台均不在该设置范围内。

历史验证：API 28 模拟器实际重启后，
关闭时记录禁用结果且不启动；开启时设置跨重启保留，
并由接收器打开 MainActivity。
Android 10 及以上的通知回退及厂家限制仍需对应设备验证。

```sh
./build-apk.sh
```
